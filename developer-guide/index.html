1. The Problem Statement & The Solution Architecture

The Core Problem in Defense & Enterprise Security

In defense and mission-critical production facilities (such as Bharat Electronics Limited), digital infrastructure handles confidential schematics, radar telemetry software, and personnel access to classified physical/digital sectors. Standard industry architectures suffer from three critical flaws:

  1. Single Points of Failure (Centralized IAM): When all user accounts, password hashes, and access privileges are stored in a centralized directory service (e.g., standard LDAP, Active Directory, or a single SQL database), a single compromised root account or database SQL injection completely compromises the entire organizational security boundary.
  2. Mutable Audit Trails (Log Forgery & Erasure): Standard server access logs and database audit tables can be modified or truncated by malicious insiders, compromised administrators, or attackers who gain root shell access. Consequently, post-incident forensic investigations cannot trust the log files.
  3. Unanchored Digital Assets (Silent Tampering): Binary executables, radar firmware, and confidential CAD drawings reside on distributed file shares. If an adversary or supply-chain attacker alters a single byte of firmware, existing systems have no decentralized, immutable cryptographic anchor to detect the modification.

The BEL TrustChain Solution

Team ShieldX designed BEL TrustChain as a 3-tier decentralized security architecture combining high-speed web services with an independent Proof-of-Work blockchain ledger:

  • Self-Sovereign Decentralized Identifiers (DIDs): Cryptographically unique W3C-compliant identities (did:bel:<hex>) issued on-chain with immutable clearance tiers (Levels 1 to 5).
  • Real-Time Clearance Authorization & Blockchain Logging: Access control checks enforce mathematical clearance inequality ($Clearance_{user} \ge Clearance_{resource}$ OR $Grant_{active}$). Both granted and denied access attempts are permanently mined into the blockchain ledger for absolute forensic non-repudiation.
  • Hybrid Digital Asset Tokenization: Sensitive physical files are maintained securely off-chain in encrypted storage, while their 256-bit cryptographic SHA-256 digests are minted into immutable blockchain tokens anchored to the owner's DID.
  • Zero-Hang Dual-Engine Database: A resilient dual-storage engine connecting to MongoDB Atlas when available, while seamlessly falling back to an in-memory/JSON store for 100% offline uptime and instant demonstration.

4. Deep Dive: Python Blockchain Consensus Engine

The blockchain microservice is located in blockchain-service/ and comprises three core modules: blockchain.py, models.py, and api.py.

4.1 Block Computation & Proof-of-Work (`blockchain.py`)

Every block is linked cryptographically to the previous block via SHA-256. Proof-of-Work requires finding a nonce such that the hash has a specific prefix (e.g., two leading zeroes "00"): 

class Block:
    def __init__(self, index: int, transactions: list, previous_hash: str, nonce: int = 0, timestamp: float = None):
        self.index = index
        self.timestamp = timestamp or time.time()
        self.transactions = transactions
        self.previous_hash = previous_hash
        self.nonce = nonce
        self.hash = self.compute_hash()

    def compute_hash(self) -> str:
        block_string = json.dumps({
            "index": self.index,
            "timestamp": self.timestamp,
            "transactions": self.transactions,
            "previous_hash": self.previous_hash,
            "nonce": self.nonce
        }, sort_keys=True)
        return hashlib.sha256(block_string.encode('utf-8')).hexdigest()
Why sort_keys=True is Essential: In JSON serialization, dictionary key ordering is arbitrary. Specifying sort_keys=True guarantees identical string formatting, ensuring that the hash computation is 100% deterministic across all platforms.

4.2 Proof-of-Work Mining Loop

def proof_of_work(self, block: Block) -> str:
    block.nonce = 0
    computed_hash = block.compute_hash()
    target = '0' * self.DIFFICULTY

    while not computed_hash.startswith(target):
        block.nonce += 1
        computed_hash = block.compute_hash()

    return computed_hash

5. Deep Dive: Express Backend & Resilient Dual-Storage Engine

The Node.js backend handles web traffic, parses JWT credentials, verifies clearance tiers, computes file digests, and communicates with the Python blockchain engine over REST API.

5.1 The Transparent Proxy Pattern (`backend/models/`)

Each database model wraps both Mongoose (for remote MongoDB Atlas) and the local offline engine via a JavaScript Proxy: 

// Example from User.js
const MongooseUser = mongoose.models.User || mongoose.model('User', userSchema);
const OfflineUser = createOfflineModel('users', { matchPassword: true });

const UserProxy = new Proxy(MongooseUser, {
  get(target, prop) {
    if (getIsConnected()) {
      return target[prop]; // Route to MongoDB Atlas
    }
    if (typeof OfflineUser[prop] === 'function') {
      return OfflineUser[prop].bind(OfflineUser); // Route to Local Store
    }
    return target[prop];
  },
});

module.exports = UserProxy;

6. Decentralized Identifiers (DIDs) & Identity Lifecycle

In BEL TrustChain, identities conform to the W3C standard scheme: did:bel:<hex_hash>.

Issuance vs. Revocation:

  • Issuance: Admin creates a DID credential with a specified role and clearance tier (1–5). A transaction of type IDENTITY_ISSUE is mined into a new block.
  • Revocation: When an identity is revoked, an IDENTITY_REVOKE transaction is mined. The historical issuance block remains immutable, but the active state evaluator sees the revocation and denies all subsequent access attempts.

7. Role & Clearance-Based Access Control (RBAC)

The system enforces a 5-tier clearance hierarchy:

TierClassificationSample Defense Resources
Level 1PublicGENERAL_CAMPUS_BULLETIN
Level 2ConfidentialINTERNAL_PROJECT_SPECS
Level 3SecretFINANCIAL_AUDIT_LEDGER
Level 4Top SecretDEFENSE_RADAR_SCHEMATICS
Level 5CommandMISSILE_GUIDANCE_SYSTEM

Policy Evaluation Rule

Access is ALLOWED if: $$\text{Subject Clearance Level} \ge \text{Resource Required Clearance}$$ OR if an active on-chain ACCESS_GRANT override exists. Otherwise, access is DENIED. Every single decision is permanently mined onto the blockchain ledger.

8. Digital Asset Tokenization & Live Tamper Demo

When an asset is uploaded, Node.js computes its SHA-256 checksum: 

const crypto = require('crypto');
function calculateFileHash(filePath) {
  const fileBuffer = fs.readFileSync(filePath);
  return crypto.createHash('sha256').update(fileBuffer).digest('hex');
}

The 64-character hex hash is anchored onto the blockchain. During verification, the current file on disk is re-hashed. If an attacker has changed even a single byte on disk, the re-computed hash diverges from the blockchain anchor, triggering an instant Tamper Alert.

9. Frontend Web Client Architecture

The frontend uses Vanilla JavaScript with modular handlers for auth, identity, access control, asset tokens, and audit inspection.

The apiRequest() helper in frontend/js/api.js automatically attaches the Bearer JWT token from localStorage and manages JSON headers transparently: 

async function apiRequest(endpoint, options = {}) {
  const token = localStorage.getItem('sih_token');
  const headers = { ...options.headers };

  if (token) headers['Authorization'] = `Bearer ${token}`;
  if (options.body && !(options.body instanceof FormData)) {
    headers['Content-Type'] = 'application/json';
  }

  const response = await fetch(endpoint, { ...options, headers });
  const data = await response.json();
  return { ok: response.ok, status: response.status, data };
}

13. Evaluator Viva Defense Q&A

Q: Why use a custom Python blockchain instead of Ethereum?
A: A custom lightweight Proof-of-Work blockchain provides zero transaction gas fees, zero external network dependencies, microsecond block mining, and 100% explainability during academic and defense evaluations.
Q: How does the system handle tamper detection?
A: The physical file is hashed using SHA-256 upon upload and permanently anchored to a mined block. When verified, the file is re-hashed; any unauthorized modification changes the computed digest, alerting the security team immediately.
